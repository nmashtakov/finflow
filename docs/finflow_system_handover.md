# FinFlow — описание текущей системы и контекст для нового CRM-модуля

Дата подготовки: 09.05.2026  
Назначение документа: передача текущего состояния системы другому агенту / разработчику перед проектированием и реализацией нового CRM-модуля.

## 1. Краткое резюме

`FinFlow` — это Django-монолит для управления личными финансами. В системе уже есть:

- учет транзакций;
- справочники проектов, категорий, подкатегорий, счетов и валют;
- ручной ввод транзакций;
- импорт транзакций из CSV/XLSX;
- staging-пайплайн для импорта с нормализацией, авторазметкой и ручной проверкой;
- правила категоризации для повторных импортов;
- механизм связок между транзакциями;
- аналитический дашборд;
- модуль прогнозирования бюджета;
- интеграция со staging-импортом событий Bybit.

Система уже вышла за рамки простой таблицы расходов: сейчас это базовая финансовая платформа со справочниками, контролем качества данных, аналитикой и полуавтоматическим импортом.

Планируемое развитие: добавить отдельный CRM-модуль для ведения LEGO-бизнеса, не ломая существующий финансовый контур.

## 2. Технологический стек и архитектура

### 2.1. Backend

- `Python 3.9`
- `Django 4.2`
- `PostgreSQL`
- стандартная модель пользователя Django (`auth_user`), кастомной модели пользователя нет.

### 2.2. Frontend

- серверный рендеринг через Django templates;
- `Bootstrap 5`;
- `jQuery`;
- `DataTables`;
- `Select2` в отдельных экранах;
- `Chart.js` для графиков;
- `Feather Icons` и `Font Awesome` для иконок.

Это не SPA. Логика в основном распределена между Django views, шаблонами и небольшими JS-скриптами на страницах.

### 2.3. Деплой и окружение

Система запускается через `docker-compose` и содержит минимум такие сервисы:

- `postgres` — основная БД;
- `django` — веб-приложение;
- `airflow_webserver`;
- `airflow_scheduler`.

Airflow уже присутствует в инфраструктуре и может использоваться для фоновых задач, но в текущем пользовательском сценарии основной контур — это Django + PostgreSQL.

### 2.4. Структура Django apps

- `accounts` — авторизация, регистрация, профиль, список пользователей для superuser.
- `core` — базовые доменные модели, настройки, дашборды, справочники, валюты, счета.
- `transactions` — транзакции, импорт, review flow, правила категоризации, связки, Bybit staging.
- `forecasting` — месячная аналитика и прогноз бюджета.

## 3. Навигация по системе

Основное меню сейчас содержит:

- `Аналитика`
- `Прогноз`
- `Транзакции`
- `Пользователи` — только для superuser
- `Проекты и категории`
- `Счета`

Важно: UI уже организован модульно. Новый CRM логично добавлять как отдельный раздел в боковое меню, а не смешивать с существующими экранами транзакций.

## 4. Роли и доступы

### 4.1. Обычный пользователь

Может:

- работать только со своими данными;
- создавать проекты, категории, подкатегории, счета, транзакции;
- импортировать транзакции;
- работать с аналитикой, прогнозом и связками;
- настраивать Bybit-подключения только для себя.

### 4.2. Superuser

Дополнительно:

- видит список пользователей;
- имеет ссылку на стандартную Django admin-панель.

Отдельной сложной ролевой модели сейчас нет.

## 5. Основные доменные сущности

## 5.1. Пользователь и настройки

### `User`

Используется стандартная модель Django.

### `UserPreferences`

Хранит пользовательские дефолты:

- `default_account`
- `default_project`

Эти значения используются при создании транзакций и в части сценариев импорта.

## 5.2. Финансовая иерархия

### `Project`

Поля:

- `user`
- `name`
- `description`
- `status` (`active`, `archived`, `deleted`)

Смысл: верхний уровень группировки финансового учета. Примеры: `Личные финансы`, отдельные направления, счета банков, будущие бизнес-направления.

### `Category`

Поля:

- `user`
- `name`
- `status`

Смысл: логическая категория расходов/доходов.

### `Subcategory`

Поля:

- `user`
- `name`
- `status`

Смысл: более детальная детализация категории.

### `ExpenseLink`

Ключевая сущность текущей системы.

Поля:

- `user`
- `project`
- `category`
- `subcategory` (nullable)
- `status`

Смысл: связка `Проект -> Категория -> Подкатегория`.  
Именно `ExpenseLink` прикрепляется к транзакции, а не просто категория сама по себе.

Это важная архитектурная особенность:

- категории и подкатегории существуют глобально в рамках пользователя;
- но используются внутри проектов через отдельные связки;
- одна и та же категория может присутствовать в разных проектах.

## 5.3. Счета и остатки

### `Account`

Поля:

- `user`
- `name`
- `account_type` (`normal`, `debt`, `saving`)
- `currency`
- `status` (`active`, `archived`, `deleted`)
- `include_in_total`
- `show_in_expenses`
- `credit_limit`
- `account_target`
- `total_debt`

Правила:

- название счета уникально в рамках пользователя;
- удаление реализовано как soft delete через `status='deleted'`;
- можно назначать счет по умолчанию;
- у каждого счета есть валюта;
- часть полей нужна для аналитики и сверки, а не только для хранения метаданных.

### `AccountBalanceSnapshot`

Поля:

- `account`
- `snapshot_date`
- `balance`
- `note`

Смысл: фиксация фактического баланса счета на определенную дату.

Используется для:

- сверки корректности транзакций;
- обнаружения расхождений между расчетным и реальным балансом;
- чек-листа качества финансовых данных.

## 5.4. Транзакции

### `Transaction`

Поля:

- `account`
- `expense_link`
- `amount`
- `currency`
- `date`
- `transaction_type` (`income`, `expense`, `transfer`)
- `comment`
- `related_transaction`
- `parent_transaction`
- `is_split_parent`
- `created_at`

Ключевые правила:

- положительная сумма трактуется как доход;
- отрицательная сумма трактуется как расход;
- `transaction_type` в большинстве сценариев выводится именно из знака суммы;
- одна транзакция может быть разделена на несколько дочерних частей;
- родительская операция после split помечается `is_split_parent=True` и скрывается из рабочих списков.

## 5.5. Валюты

### `Currency`

Поля:

- `code`
- `name`
- `status`

Смысл: справочник доступных валют.

### `CurrencyRate`

Поля:

- `date`
- `currency`
- `amount`

Смысл: курс валюты к RUB на дату.

Особенности:

- `RUB` всегда считается равным 1;
- `USDT` дублируется по курсу `USD`;
- курсы загружаются из ЦБ РФ;
- отсутствующие дневные ставки могут быть дозаполнены предыдущим известным значением.

## 5.6. Связки между транзакциями

### `TransactionLinkGroup`

Типы:

- `reimbursement` — возврат / компенсация
- `transfer_pair` — перевод между счетами
- `exchange_pair` — обмен

### `TransactionLinkItem`

Роли:

- `primary`
- `offset`
- `outgoing`
- `incoming`

Смысл:

- объединяет несколько транзакций в одну смысловую группу;
- нужен для корректной аналитики;
- особенно важен для возвратов, внутренних переводов и обменов.

## 5.7. Импортный staging-контур

### `ImportSource`

Описывает источник импорта:

- `generic`
- `tinkoff`
- `alfa`
- `bybit`
- и т.д.

### `TransactionImportSession`

Поля:

- `user`
- `source`
- `status`
- `total_rows`
- `matched_rows`
- `needs_review_rows`
- `normalizer_version`
- `created_at`
- `original_name`
- `columns`
- `sample_rows`
- `rows`
- `metadata`

Смысл: контейнер для одной сессии импорта. Хранит исходные строки, превью, состояние пайплайна и служебные метаданные.

Статусы:

- `uploaded`
- `normalized`
- `categorized`
- `review`
- `completed`
- `failed`

### `ImportedTransaction`

Промежуточная staging-сущность между сырым импортом и основной таблицей `Transaction`.

Хранит:

- сырой payload;
- нормализованный payload;
- нормализованные поля даты/суммы/валюты;
- направление операции;
- нормализованный merchant / description / source category;
- fingerprint;
- статус категоризации;
- matched rule;
- resolved expense link;
- финальную транзакцию после публикации в core;
- split-структуру внутри review flow.

### `CategorizationRule`

Правило авторазметки импортов.

Поля:

- `source`
- `user` (может быть `null` для системных правил)
- `name`
- `priority`
- `confidence`
- `conditions` (JSON)
- `action_expense_link`
- `action_sign`
- `is_active`

Поддерживаемые поля условий:

- `merchant_norm`
- `description_norm`
- `source_category_norm`
- `direction`
- `currency`

Поддерживаемые операторы:

- `equals`
- `contains`
- `regex`

### `CategorizationFeedback`

Хранит след ручной разметки пользователя:

- какая транзакция была изменена;
- какое правило было до этого;
- в какую связку расходов ее переназначили;
- было ли создано новое правило.

## 5.8. Bybit staging

### `BybitConnection`

Поля:

- `user`
- `name`
- `api_key`
- `api_secret`
- `is_testnet`
- `is_active`
- `last_sync_at`

### `BybitSyncRun`

Хранит историю синхронизаций:

- статус;
- диапазон дат;
- потоки;
- количество fetched / inserted / updated;
- сообщение.

### `BybitExternalEvent`

Сырые события, загруженные из Bybit, но еще не опубликованные в основную таблицу транзакций.

## 5.9. Forecasting

### `MonthlyBudgetPlan`

Хранит сохраненный бюджетный план на месяц:

- пользователь;
- проект;
- базовый месяц;
- целевой месяц плана;
- валюта;
- окно распределения;
- прогноз доходов/расходов;
- итоговый план.

### `MonthlyBudgetLine`

Строки плана по категориям:

- категория;
- тип расхода (`regular` / `risk`);
- средняя сумма;
- доля;
- рекомендуемая сумма;
- плановая сумма.

## 6. Пользовательские сценарии

## 6.1. Регистрация и первичная инициализация

После регистрации:

- создается пользователь;
- автоматически вызывается `create_default_finance_structure(user)`;
- пользователю создается проект `Личные финансы`;
- создается стартовый набор категорий и подкатегорий;
- создаются базовые `ExpenseLink` для этой структуры.

Иными словами, система умеет сразу стартовать не с пустой БД, а с базовым финансовым каталогом.

## 6.2. Работа со справочником проектов и категорий

Экран: `Проекты и категории`

Функциональность:

- создание проекта;
- редактирование проекта;
- удаление проекта;
- назначение проекта по умолчанию;
- добавление категории внутрь проекта;
- редактирование и удаление категории в рамках проекта;
- добавление, редактирование и удаление подкатегории;
- дерево по умолчанию открывается свернутым;
- после действий система может открывать нужный узел через query-параметры.

Архитектурно важно:

- категория не принадлежит проекту напрямую на уровне модели;
- принадлежность формируется через `ExpenseLink`.

## 6.3. Работа со счетами

Экран: `Счета`

Функциональность:

- создание счета;
- редактирование счета;
- мягкое удаление;
- назначение счета по умолчанию;
- отображение статусов и признаков включения в баланс / расходы;
- фиксация баланса по дням;
- копирование баланса “без изменений” на текущую дату;
- история фиксаций;
- автоматический расчет расхождения между фактом и моделью.

Этот экран уже делает не только CRUD, но и верификацию качества учета.

## 6.4. Ручное добавление транзакций

Экран: `Транзакции`

Форма создания включает:

- дата и время;
- сумма;
- валюта;
- счет;
- проект/категория/подкатегория через `ExpenseLink`;
- комментарий.

Особенности:

- дата по умолчанию = текущее время;
- валюта по умолчанию = `RUB`, если она есть в справочнике;
- могут подставляться `default_account` и `default_project`;
- тип транзакции вычисляется по знаку суммы.

## 6.5. Список транзакций

Таблица транзакций поддерживает:

- server-side пагинацию;
- сортировку;
- глобальный поиск;
- фильтр по проекту;
- фильтр по счету;
- фильтр по категории;
- фильтр по подкатегории;
- фильтр по диапазону дат.

Есть инлайн-редактирование прямо в строке:

- дата;
- сумма;
- валюта;
- счет;
- проект;
- категория;
- подкатегория;
- комментарий.

Также доступны:

- удаление транзакции;
- split транзакции на несколько частей;
- экспорт в CSV с набором колонок и режимами исключения технических движений.

Ограничения:

- нельзя удалить транзакцию, если она участвует в связке;
- нельзя делить транзакцию, если она уже разделена или участвует в связке.

## 6.6. Импорт транзакций из CSV/XLSX

Экран: `Импорт из файла`

Текущий flow:

1. Загрузка файла.
2. Выбор preset источника:

- `auto`
- `tinkoff`
- `alfa`
- `t_business`
- `other`

3. Если загружен Excel и в нем несколько листов — отдельный шаг выбора целевого листа.
4. Далее один из сценариев:

- либо отдельный упрощенный банковский шаг;
- либо форма сопоставления колонок.

### Сопоставление колонок

Форма умеет:

- выбирать колонку даты;
- колонку суммы;
- колонку валюты;
- колонку типа операции;
- колонку счета;
- колонку проекта;
- колонку категории;
- колонку подкатегории;
- колонку комментария;
- задавать default currency;
- задавать default account / account name;
- задавать default project / project name;
- задавать income/expense markers.

### Автоопределение

Есть эвристики автоопределения колонок:

- по заголовку;
- по sample values;
- по валютным кодам;
- по структуре чисел;
- по типичным словам вроде `валюта`, `amount`, `date`, `category` и т.д.

### Особенности обработки файлов

- CSV читается с автоопределением разделителя;
- Excel читается через `pandas/openpyxl`;
- пустые строки отбрасываются;
- значения приводятся к JSON-safe виду;
- поддерживаются числа и с точкой, и с запятой.

## 6.7. Нормализация, staging и review flow

После загрузки файл не сразу попадает в `Transaction`.

Сначала происходит:

1. `normalize_rows(...)`
2. `categorize_session(...)`
3. при необходимости — ручной review
4. `finalize_session(...)`

### Что делает `normalize_rows`

- преобразует строки файла в `ImportedTransaction`;
- использует normalizer в зависимости от источника;
- вычисляет fingerprint;
- отсеивает явные дубли;
- собирает duplicate candidates;
- пишет staging-объекты;
- сохраняет статус импорт-сессии.

### Что делает `categorize_session`

Пытается автоматически назначить `ExpenseLink` через:

- словарное сопоставление `project/category/subcategory`;
- специальные generated cases;
- системные правила;
- пользовательские правила.

Результат:

- часть строк получает `AUTO`;
- часть уходит в `NEEDS_REVIEW`.

### Экран review

Экран `Проверка транзакций` позволяет:

- фильтровать строки по описанию и source category;
- массово назначать категорию;
- назначать категорию по одной строке;
- менять комментарий;
- вручную создавать правило из исправления;
- делить staging-транзакцию на части;
- финализировать сессию.

### Финализация

`finalize_session(...)`:

- берет только `AUTO` и `MANUAL`;
- создает обычные `Transaction`;
- привязывает их обратно к `ImportedTransaction.final_transaction`;
- переводит сессию в `COMPLETED` или оставляет в `REVIEW`, если что-то еще не разобрано.

## 6.8. Работа с дублями

Во время нормализации система:

- вычисляет fingerprint операции;
- не создает явный дубль сразу;
- кладет его в `duplicate_candidates`.

Потом пользователь может вручную восстановить выбранные дубли как реальные операции.

Это важно для банковских выгрузок, где одинаковые строки не всегда означают ошибку.

## 6.9. Правила категоризации

Экран: `Правила разметки`

Позволяет:

- просматривать пользовательские правила;
- фильтровать их по источнику и активности;
- удалять правило.

Правила строятся на нормализованных полях, а не на сыром тексте “как есть”.  
Это уже полноценный полуэкспертный слой поверх импорта.

## 6.10. Связки операций

Экран: `Связки операций`

Назначение:

- связывать возвраты с исходными расходами;
- связывать переводы между своими счетами;
- связывать переводы между людьми;
- связывать обменные операции.

Поддерживается:

- список рекомендаций “требуют внимания”;
- подбор кандидатов;
- ручное создание связки;
- удаление связки;
- быстрый поиск второй операции по комментарию / счету / категории / ID.

Эта механика затем влияет на аналитику:

- возвраты могут вычитаться из расходов;
- внутренние переводы не должны искажать реальный cashflow.

## 6.11. Bybit staging и импорт из API

Экран: `API подключения` и `Bybit staging`

Сценарий:

1. пользователь заводит Bybit API connection;
2. запускает sync по выбранным потокам и диапазону дат;
3. события попадают не в основную таблицу транзакций, а в `BybitExternalEvent`;
4. из staging-таблицы создается обычная import session;
5. дальше сессия проходит стандартный review/finalize flow.

Преимущества подхода:

- интеграция не ломает основную книгу транзакций;
- есть промежуточный безопасный слой;
- можно повторно синхронизировать и фильтровать источники до публикации.

## 7. Аналитика

## 7.1. Дашборд

Экран: `Аналитика`

Сейчас это не простой summary, а развитый аналитический модуль.

Поддерживаемые фильтры:

- дата с;
- дата по;
- валюта просмотра;
- счета (multi-select);
- проекты (multi-select);
- категории (multi-select);
- подкатегории (multi-select);
- валюта операций (multi-select);
- тип (`income` / `expense` / все);
- режим расходов:
  - `net` — с учетом возвратов;
  - `cashflow` — полный денежный поток;
- диапазон графиков:
  - прошлый + текущий год;
  - текущий фильтр;
  - все время;
- `focus_month` для drilldown в конкретный месяц.

### Что считает дашборд

- суммарные поступления;
- суммарные расходы;
- сальдо периода;
- объем возвратов;
- средний расход;
- число операций;
- число операций без курса;
- количество доходных и расходных операций;
- summary по проектам;
- summary по категориям и подкатегориям;
- балансоподобные totals по счетам в валюте отчета;
- top categories;
- месячные графики потока;
- кумулятивный график;
- pivot по проектам/категориям/подкатегориям с drilldown.

### Особенности расчетов

- суммы при необходимости конвертируются в `report_currency`;
- возвраты и компенсации учитываются через `TransactionLinkGroup`;
- переводы между счетами не должны попадать в обычные расходы как бытовые траты;
- для pivot и аналитики используются уже очищенные суммы после логики reimbursement/linking.

## 7.2. Checklist и контроль качества

Есть отдельный чек-лист периода:

- есть ли незавершенные import sessions;
- есть ли операции в review;
- есть ли неподвязанные возвраты и переводы;
- есть ли свежие фиксации баланса по активным счетам.

Это важная особенность зрелости системы: она уже умеет проверять качество учета, а не только хранить операции.

## 7.3. Drilldown по ячейке дашборда

Есть endpoint для получения транзакций по конкретной ячейке аналитики:

- месяц;
- проект;
- категория;
- подкатегория;
- дополнительные фильтры.

Это нужно учитывать при развитии аналитических модулей: дашборд не только отображает агрегаты, но и умеет расшифровывать их до списка операций.

## 8. Прогнозирование

Экран: `Прогноз`

Модуль умеет:

- строить отчет по загруженному файлу;
- выбирать проект;
- выбирать месяц;
- выбирать валюту отчета;
- анализировать аномалии;
- выделять регулярные и рисковые расходы;

- бюджет раскладывается по окну распределения.

Фактически это уже отдельный аналитический подсервис внутри продукта.

## 11. Технические нюансы и ограничения

### 11.1. Timezone

В `settings.py` указан `TIME_ZONE = 'UTC'`, но многие пользовательские даты локализуются через `timezone.localtime(...)`.

Это значит:

- данные хранятся timezone-aware;
- при развитии CRM нужно аккуратно обращаться с датами, дедлайнами, событиями и временными зонами.

### 11.2. Нет custom user model

Если CRM потребует расширенный профиль пользователя, лучше делать отдельную связанную модель, а не пытаться поздно заменить `AUTH_USER_MODEL`.

### 11.3. Soft delete используется не везде одинаково

Счета, проекты, категории и подкатегории во многом живут через `status`.  
При проектировании CRM лучше сразу решить:

- будет ли единый паттерн статусов;
- нужен ли мягкий архив вместо физического удаления.

### 11.4. ExpenseLink — критически важная сущность

Во многих местах системы логика завязана именно на `ExpenseLink`.  
Если CRM позже будет связан с финансами, важно заранее продумать:

- будет ли CRM создавать свои financial mappings;
- будет ли отдельный слой “операция CRM -> финансовая категория”.

### 11.5. Импортный pipeline уже сложный

Новый агент должен понимать, что импорт в системе — это уже не просто “загрузили CSV и вставили в Transaction”.

Есть:

- import session;
- staging-таблица;
- normalization;
- deduplication;
- auto-categorization;
- review;
- finalize.

Если CRM получит импорт заказов / продаж / остатков, разумно переиспользовать этот архитектурный паттерн.

### 11.6. Airflow уже есть в инфраструктуре

Если CRM будет требовать:

- регулярные sync;
- автоматические напоминания;
- расчеты;
- выгрузки;

то Airflow можно использовать как штатный механизм фоновых задач.

## 12. Что важно сохранить при добавлении CRM

Новый модуль не должен разрушить финансовую часть. Важно сохранить:

- изоляцию пользовательских данных;
- текущую структуру Django apps;
- единый визуальный язык;
- работу текущих справочников и транзакций;
- независимость финансового контура;
- возможность при необходимости связывать CRM-события с финансами, но не смешивать их напрямую без явного слоя интеграции.

## 13. Подтвержденный контекст нового CRM-модуля

Подтверждено только следующее:

- в систему планируется добавить новый отдельный модуль;
- модуль будет CRM для ведения LEGO-бизнеса;
- текущий модуль личных финансов остается самостоятельным и продолжает существовать.

То есть задача не в “переделке FinFlow в CRM”, а в добавлении второй крупной предметной области в тот же продукт.
